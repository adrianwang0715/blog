## 4.7   并行计算

从 20 世纪 70 年代到 21 世纪中期，单个处理器核心的速度以指数级增长。这种速度提升很大程度上是通过提高 *时钟频率（clock frequency）* 来实现的，也就是处理器执行基本操作的速率。然而到了 21 世纪中期，由于功耗和散热的限制，这种指数级增长戛然而止，此后单个处理器核心的速度增长变得缓慢得多。取而代之的是，CPU 制造商开始在同一颗处理器中放置多个核心，使得更多操作能够同时执行。

并行并不是一个新概念。大规模并行机器已经被使用了几十年，主要用于科学计算和数据分析。即使在只有单个处理器核心的个人计算机中，操作系统和解释器也提供了并发（concurrency）的抽象。这是通过 *上下文切换（context switching）* 实现的，也就是在不同的任务之间快速切换，而不必等待它们完成。因此，多个程序可以在同一台机器上并发运行，即使这台机器只有一个处理核心。

考虑到当前处理器核心数量不断增长的趋势，单个应用程序现在必须利用并行才能运行得更快。在单个程序内部，计算的安排必须使得尽可能多的工作能够并行完成。然而，并行给编写正确的代码带来了新的挑战，尤其是在存在共享的可变状态时。

对于那些可以在函数式模型中高效求解、且没有共享可变状态的问题，并行几乎不会带来什么麻烦。纯函数提供了 *引用透明性（referential transparency）*，这意味着表达式可以被替换为其值，反之亦然，而不会影响程序的行为。这使得互不依赖的表达式可以并行求值。正如上一节所讨论的，MapReduce 框架允许以极少的程序员工作量来指定并并行运行函数式程序。

遗憾的是，并非所有问题都能用函数式编程高效地求解。Berkeley View 项目在科学与工程领域中识别出了[十三种常见的计算模式](http://view.eecs.berkeley.edu/wiki/Dwarf_Mine)，其中只有一种是 MapReduce。其余模式都需要共享状态。

在本节余下的部分中，我们将看到可变共享状态如何给并行程序引入 bug，以及许多防止这类 bug 的方法。我们将在两个应用的背景下考察这些技术：一个网络[爬虫（crawler）](../examples/parallel/crawler.py.html)和一个粒子[模拟器（simulator）](../examples/parallel/particle.py.html)。

### 4.7.1   Python 中的并行

在深入探讨并行的细节之前，让我们先来探索 Python 对并行计算的支持。Python 提供了两种并行执行的方式：线程（thread）和多进程（multiprocessing）。

**线程（Threading）**。在 *线程（threading）* 中，单个解释器内存在多个执行的"线程"。每个线程独立于其他线程执行代码，尽管它们共享相同的数据。然而，CPython 解释器（Python 的主要实现）一次只在一个线程中解释代码，通过在它们之间切换来提供并行的假象。另一方面，解释器外部的操作，例如写入文件或访问网络，则可能并行运行。

`threading` 模块包含的类可以创建并同步线程。下面是一个多线程程序的简单示例：

```python
>>> import threading
>>> def thread_hello():
        other = threading.Thread(target=thread_say_hello, args=())
        other.start()
        thread_say_hello()
```

```python
>>> def thread_say_hello():
        print('hello from', threading.current_thread().name)
```

```python
>>> thread_hello()
hello from Thread-1
hello from MainThread
```

`Thread` 构造函数创建一个新线程。它需要一个新线程应当运行的目标函数，以及传给该函数的参数。对 `Thread` 对象调用 `start` 将其标记为可以运行。`current_thread` 函数返回与当前执行线程关联的 `Thread` 对象。

在这个示例中，两次打印可以以任意顺序发生，因为我们没有以任何方式对它们进行同步。

**多进程（Multiprocessing）**。Python 还支持 *多进程（multiprocessing）*，它允许一个程序生成多个解释器，也就是多个 *进程（process）*，每个进程都可以独立运行代码。这些进程通常不共享数据，因此任何共享状态都必须在进程之间传递。另一方面，进程会按照底层操作系统和硬件所提供的并行程度来并行执行。因此，如果 CPU 有多个处理器核心，Python 进程就可以真正并发运行。

`multiprocessing` 模块包含用于创建和同步进程的类。下面是使用进程的 hello 示例：

```python
>>> import multiprocessing
>>> def process_hello():
        other = multiprocessing.Process(target=process_say_hello, args=())
        other.start()
        process_say_hello()
```

```python
>>> def process_say_hello():
        print('hello from', multiprocessing.current_process().name)
```

```python
>>> process_hello()
hello from MainProcess
>>> hello from Process-1
```

正如这个示例所展示的，`multiprocessing` 中的许多类和函数都类似于 `threading` 中的那些。这个示例还展示了缺乏同步如何影响共享状态，因为显示内容也可以被视为共享状态。在这里，交互式进程的解释器提示符出现在另一个进程的打印输出之前。

### 4.7.2   共享状态的问题

为了进一步说明共享状态的问题，让我们看一个在两个线程之间共享的计数器的简单示例：

```python
import threading
from time import sleep

counter = [0]

def increment():
    count = counter[0]
    sleep(0) # try to force a switch to the other thread
    counter[0] = count + 1

other = threading.Thread(target=increment, args=())
other.start()
increment()
print('count is now: ', counter[0])
```

在这个程序中，两个线程试图递增同一个计数器。CPython 解释器几乎可以在任何时刻在线程之间切换。只有最基本的操作是 *原子性的（atomic）*，也就是说它们看起来是瞬间发生的，在其求值或执行过程中不可能发生切换。递增一个计数器需要多个基本操作：读取旧值、给它加一、写入新值。解释器可以在这些操作中的任何一个之间切换线程。

为了展示当解释器在错误的时刻切换线程时会发生什么，我们尝试通过睡眠 0 秒来强制发生一次切换。当这段代码运行时，解释器常常确实会在 `sleep` 调用处切换线程。这可能导致如下的操作序列：

```python
Thread 0                    Thread 1
read counter[0]: 0
                            read counter[0]: 0
calculate 0 + 1: 1
write 1 -> counter[0]
                            calculate 0 + 1: 1
                            write 1 -> counter[0]
```

最终结果是计数器的值为 1，尽管它被递增了两次！更糟糕的是，解释器可能极少在错误的时刻切换，这使得该问题难以调试。即使有 `sleep` 调用，这个程序有时会产生正确的计数 2，有时会产生错误的计数 1。

这个问题只在存在共享数据、且该数据可能在一个线程访问它时被另一个线程修改的情况下才会出现。这样的冲突称为 *竞态条件（race condition）*，它是只存在于并行世界中的一类 bug 的例子。

为了避免竞态条件，可能被多个线程修改和访问的共享数据必须防止并发访问。例如，如果我们能确保线程 1 只在线程 0 访问完计数器之后才访问它，或者反过来，我们就能保证计算出正确的结果。如果共享数据受到保护而不会被并发访问，我们就说它是 *同步的（synchronized）*。在接下来几个小节中，我们将看到多种提供同步的机制。

### 4.7.3   什么时候不需要同步

在某些情况下，如果并发访问不会导致错误的行为，那么对共享数据的访问就不需要同步。最简单的例子是只读数据。由于这类数据从不被修改，所有线程无论何时访问该数据，都会读到相同的值。

在少数情况下，被修改的共享数据可能不需要同步。然而，要理解何时属于这种情况，需要深入了解解释器以及底层软硬件的工作方式。考虑下面这个示例：

```python
items = []
flag = []

def consume():
    while not flag:
        pass
    print('items is', items)

def produce():
    consumer = threading.Thread(target=consume, args=())
    consumer.start()
    for i in range(10):
        items.append(i)
    flag.append('go')

produce()
```

在这里，生产者线程向 `items` 中添加条目，而消费者会一直等待，直到 `flag` 非空。当生产者完成条目添加后，它向 `flag` 中添加一个元素，从而允许消费者继续执行。

在大多数 Python 实现中，这个示例都能正确工作。然而，其他编译器和解释器（甚至硬件本身）中一个常见的优化是：对单个线程中彼此之间不存在数据依赖的操作进行重排序。在这样的系统中，语句 `flag.append('go')` 可能会被移动到循环之前，因为两者之间不存在数据依赖。总的来说，除非你确信底层系统不会对相关操作重排序，否则应当避免写出这样的代码。

### 4.7.4   同步的数据结构

同步共享数据最简单的方法是使用一个提供同步操作的数据结构。`queue` 模块包含一个 `Queue` 类，它提供对数据的同步先进先出访问。`put` 方法向 `Queue` 中添加一个条目，`get` 方法取出一个条目。该类本身确保这些方法是同步的，因此无论线程操作如何交错，条目都不会丢失。下面是一个使用 `Queue` 的生产者/消费者示例：

```python
from queue import Queue

queue = Queue()

def synchronized_consume():
    while True:
        print('got an item:', queue.get())
        queue.task_done()

def synchronized_produce():
    consumer = threading.Thread(target=synchronized_consume, args=())
    consumer.daemon = True
    consumer.start()
    for i in range(10):
        queue.put(i)
    queue.join()

synchronized_produce()
```

除了 `Queue` 以及 `get` 和 `put` 调用之外，这段代码还有几处改动。我们将消费者线程标记为一个 *守护线程（daemon）*，这意味着程序在退出前不会等待该线程完成。这允许我们在消费者中使用无限循环。然而，我们确实需要确保主线程会退出，但只在所有条目都从 `Queue` 中被取出之后。消费者调用 `task_done` 方法来告知 `Queue` 它已处理完一个条目，而主线程调用 `join` 方法，它会等待直到所有条目都被处理完，从而确保程序只在这种情况下才退出。

一个更复杂的、使用 `Queue` 的例子是一个并行网络[爬虫（crawler）](../examples/parallel/crawler.py.html)，它会在一个网站上搜索失效链接。这个爬虫会跟随由同一站点托管的所有链接，因此它必须处理大量 URL，不断向 `Queue` 中添加新的 URL 并取出 URL 进行处理。通过使用同步的 `Queue`，多个线程可以安全地并发向该数据结构中添加和从中取出。

### 4.7.5   锁

当某个特定数据结构没有可用的同步版本时，我们必须提供自己的同步机制。*锁（lock）* 就是一种基本机制。它最多只能被一个线程 *获取（acquire）*，此后在它被先前获取它的线程 *释放（release）* 之前，其他任何线程都不能获取它。

在 Python 中，`threading` 模块包含一个 `Lock` 类来提供加锁功能。`Lock` 有 `acquire` 和 `release` 方法来获取和释放锁，而该类保证同一时刻只有一个线程能够获取它。在锁已被持有的情况下，所有其他试图获取该锁的线程都会被强制等待，直到它被释放。

为了让锁保护某一组特定的数据，所有线程都需要按照一条规则来编程：除非线程拥有那个特定的锁，否则它不会访问任何共享数据。实际上，所有线程都需要用该锁的 `acquire` 和 `release` 调用来"包裹"它们对共享数据的操作。

在并行网络[爬虫（crawler）](../examples/parallel/crawler.py.html)中，使用一个集合来跟踪任何线程已经遇到过的所有 URL，从而避免对某个特定 URL 进行多次处理（并可能陷入循环）。然而，Python 并不提供同步的集合，因此我们必须使用锁来保护对一个普通集合的访问：

```python
seen = set()
seen_lock = threading.Lock()

def already_seen(item):
    seen_lock.acquire()
    result = True
    if item not in seen:
        seen.add(item)
        result = False
    seen_lock.release()
    return result
```

这里需要一把锁，以防止在某个线程检查 URL 是否在集合中与将其添加到集合之间，另一个线程把该 URL 添加进集合。此外，向集合中添加并不是原子性的，因此并发地尝试向集合中添加可能会破坏其内部数据。

在这段代码中，我们必须小心，不要在释放锁之前返回。总的来说，我们必须确保在不再需要锁时释放它。这非常容易出错，尤其是在有异常的情况下，因此 Python 提供了一个 `with` 复合语句来替我们处理锁的获取和释放：

```python
def already_seen(item):
    with seen_lock:
        if item not in seen:
            seen.add(item)
            return False
        return True
```

`with` 语句确保在执行其代码块之前获取 `seen_lock`，并且无论由于何种原因离开该代码块时都会释放它。（`with` 语句实际上还可以用于加锁之外的操作，不过我们在此不会介绍其他用法。）

必须彼此同步的操作必须使用同一把锁。然而，两组互不相交、只需要与同一组内的操作同步的操作，应当使用两个不同的锁对象，以避免过度同步。

### 4.7.6   屏障

另一种避免对共享数据的冲突访问的方法是把程序划分为若干阶段，确保共享数据只在没有其他线程访问它的阶段中被修改。*屏障（barrier）* 通过要求所有线程都到达它之后任何一个才能继续，从而把程序划分为若干阶段。在屏障之后执行的代码不可能与屏障之前执行的代码并发。

在 Python 中，`threading` 模块通过 `Barrier` 实例的 `wait` 方法提供了屏障：

```python
counters = [0, 0]
barrier = threading.Barrier(2)

def count(thread_num, steps):
    for i in range(steps):
        other = counters[1 - thread_num]
        barrier.wait() # wait for reads to complete
        counters[thread_num] = other + 1
        barrier.wait() # wait for writes to complete

def threaded_count(steps):
    other = threading.Thread(target=count, args=(1, steps))
    other.start()
    count(0, steps)
    print('counters:', counters)

threaded_count(10)
```

在这个示例中，对共享数据的读取和写入发生在由屏障分隔的不同阶段。写入发生在同一阶段，但它们是互不相交的；这种互不相交性对于避免在同一阶段并发写入同一数据是必要的。由于这段代码被正确地同步，两个计数器最后总是 10。

多线程粒子[模拟器（simulator）](../examples/parallel/particle.py.html)以类似的方式使用屏障来同步对共享数据的访问。在模拟中，每个线程拥有若干粒子，所有粒子在多个离散时间步的过程中相互作用。一个粒子具有位置、速度和加速度，并且在每个时间步中根据其他粒子的位置计算出新的加速度。粒子的速度必须相应地更新，而它的位置则根据其速度更新。

与上面这个简单示例一样，存在一个读取阶段，在这个阶段中所有粒子的位置都被所有线程读取。每个线程在这个阶段更新自己粒子的加速度，但由于这些写入是互不相交的，它们不需要同步。在写入阶段，每个线程更新自己粒子的速度和位置。同样，这些写入是互不相交的，并且通过屏障与读取阶段隔离开来。

### 4.7.7   消息传递

避免不恰当修改共享数据的最后一种机制是完全避免对同一数据的并发访问。在 Python 中，使用多进程而不是线程自然会得到这种效果，因为进程运行在各自拥有独立数据的独立解释器中。多个进程所需的任何状态都可以通过在进程之间传递消息来通信。

`multiprocessing` 模块中的 `Pipe` 类提供了进程之间的通信通道。默认情况下它是双工的（duplex），也就是一条双向通道，不过传入参数 `False` 会得到一条单向通道。`send` 方法通过该通道发送一个对象，而 `recv` 方法接收一个对象。后者是 *阻塞的（blocking）*，这意味着调用 `recv` 的进程会一直等待，直到接收到一个对象。

下面是使用进程和管道的生产者/消费者示例：

```python
def process_consume(in_pipe):
    while True:
        item = in_pipe.recv()
        if item is None:
            return
        print('got an item:', item)

def process_produce():
    pipe = multiprocessing.Pipe(False)
    consumer = multiprocessing.Process(target=process_consume, args=(pipe[0],))
    consumer.start()
    for i in range(10):
        pipe[1].send(i)
    pipe[1].send(None) # done signal

process_produce()
```

在这个示例中，我们使用一条 `None` 消息来表示通信结束。在创建消费者进程时，我们还把管道的一端作为参数传给了目标函数。这是必要的，因为状态必须在进程之间显式共享。

粒子[模拟器（simulator）](../examples/parallel/particle.py.html)的多进程版本使用管道在每个时间步的进程之间通信粒子位置。事实上，它使用管道在进程之间建立起一整个循环流水线，以最小化通信量。每个进程把自己粒子的位置注入到它的流水线阶段中，这些位置最终会经历流水线的一整圈轮转。在轮转的每一步中，一个进程把当前位于它自己流水线阶段中的位置所产生的力施加到它自己的粒子上，这样经过一整圈轮转后，所有的力都已经施加到它的粒子上了。

`multiprocessing` 模块为进程提供了其他同步机制，包括同步队列、锁，以及从 Python 3.3 开始提供的屏障。例如，可以使用锁或屏障来同步向屏幕的打印，避免我们之前看到的那种不正确的显示输出。

### 4.7.8   同步的陷阱

虽然同步方法在保护共享状态方面很有效，但它们也可能被错误地使用：未能实现正确的同步、过度同步，或者由于死锁而导致程序挂起。

**同步不足（Under-synchronization）**。并行计算中一个常见的陷阱是忽略了对共享访问进行恰当的同步。在集合的例子中，我们需要把成员检查与插入一起同步，这样另一个线程就无法在这两个操作之间执行插入。未能把这两个操作一起同步是错误的，即使它们分别都被同步了。

**过度同步（Over-synchronization）**。另一个常见错误是过度同步程序，使得互不冲突的操作无法并发进行。举个显然的例子，我们可以通过在线程启动时获取一把主锁、并仅在线程完成时释放它，来避免所有对共享数据的冲突访问。这会把我们的整个代码串行化，从而没有任何东西并行运行。在某些情况下，这甚至可能导致我们的程序无限期挂起。例如，考虑一个消费者/生产者程序，其中消费者获取了锁却从不释放它。这会阻止生产者生产任何条目，进而使消费者什么也做不了，因为它无物可消费。

虽然这个例子很琐碎，但在实践中，程序员常常会在某种程度上过度同步他们的代码，使得代码无法充分利用可用的并行性。

**死锁（Deadlock）**。由于同步机制会使线程或进程互相等待，它们很容易受到 *死锁（deadlock）* 的影响，即两个或多个线程或进程陷入僵局，互相等待对方完成的情况。我们刚刚看到了忽略释放锁如何导致一个线程无限期地卡住。但即使线程或进程确实正确地释放了锁，程序仍然可能到达死锁。

死锁的根源是 *循环等待（circular wait）*，下面用进程来加以说明。没有进程能够继续，因为它在等待其他进程，而其他进程又在等它完成。

![figure](../img/deadlock.png)

作为一个例子，我们将用两个进程构造一个死锁。假设它们共享一条双工管道，并试图按如下方式互相通信：

```python
def deadlock(in_pipe, out_pipe):
    item = in_pipe.recv()
    print('got an item:', item)
    out_pipe.send(item + 1)

def create_deadlock():
    pipe = multiprocessing.Pipe()
    other = multiprocessing.Process(target=deadlock, args=(pipe[0], pipe[1]))
    other.start()
    deadlock(pipe[1], pipe[0])

create_deadlock()
```

两个进程都试图先接收数据。回想一下，`recv` 方法会阻塞，直到有可用的条目。由于两个进程都没有发送任何东西，双方都会无限期地等待对方发送数据，从而导致死锁。

同步操作必须被恰当地对齐以避免死锁。这可能需要先通过管道发送再接收、以相同的顺序获取多把锁，以及确保所有线程都在正确的时刻到达正确的屏障。

### 4.7.9   结论

正如我们所见，并行给编写正确且高效的代码带来了新的挑战。由于在硬件层面提高并行度的趋势在可预见的未来仍将持续，并行计算在应用程序编程中会变得越来越重要。目前有一个非常活跃的研究领域，致力于让并行对程序员来说更容易、更不易出错。我们这里的讨论只是对计算机科学这一关键领域的基础性介绍。
